# 断网演示（§7.4 第 5 条 · 任务 T4.13 / T4.16）

> 一句话：**上游不可达的时候，用户必须仍然看见屿屿在一字一字说话，而且界面右下角要写明这是离线话术。**
> 这件事此前只有代码路径，没有一次真链路证据——2026-09-28 有了，15 条判据全绿。

## 0. 环境怎么造

~~~
1) 常规实例 8080：正常 DeepSeek 上游
2) 离线实例 8081：--server.port=8081 且 DEEPSEEK_BASE_URL 指向 http://127.0.0.1:9（discard 端口，必定连不上）
3) node docs/offline-demo.mjs        # 环境变量 OFFLINE_BASE / OFFLINE_TURNS（默认 4 轮）
~~~

为什么是 4 轮：**mindisle.llm.circuit-fail-threshold: 3**，前三轮负责把熔断踩开，第 4 轮才是「短路直接走离线」那一路。

## 2. 🔴 那段必须写进文档的历史纠正：「recordDegraded 曾无条件写 offline」

v1.2.6 之前，**用户主动按停止**与**上游真的挂了**两条路共用同一条记账，
结果 ai_call_log 里一片 model='offline-empathy-bank'，看起来像「离线降级一直在工作」，
实际上是「用户按了停止」。这有两个后果：

1. 降级链路到底能不能跑通，当时没有任何证据（chat_message.degraded 全表 0 行才是真相）；
2. 反过来也会冤枉：把「停止生成」记成「上游故障」，预算与可用性统计全失真。

现在的分界写在 ChatService.abandoned() 的 javadoc 里（546–559）：**用户主动停止记 degraded、
上游违约记 failure**，两条路各自落各自的 model；上面第 3 组那条判据钉的就是「停止的那几行不许冒充离线」。

## 3. 证伪（F 组）：把 model 判据改成不会自动成立的样子

把判据里期望的模型名临时改成 offline-demo-model 再跑：

~~~
[FAIL] 3 · 🔴 每一条助手消息 model=offline-empathy-bank …  → model 取值=offline-demo-model 期望=offline-demo-model
断网演示汇总：15 项判据，通过 14 条，失败 1 条
~~~

还原之后 15/15。⇒ 这一条 PASS 不是「脚本自己说通过就通过」。

## 4. SSE 协议只有四帧（照抄手册样例前必读）

后端只发 **meta / delta / done / error**。手册 §7.5 的 T4.17 前端样例码里那支
「ev.event === "risk"」永远不会触发（风险等级在 meta.riskLevel 里带回来），
照抄会写出死分支。样例与实现的对齐已写进手册 T4.5 / T4.16 行。

## 5. 本目录**没有**证明的

- 只验了「上游不可达」这一种故障；**没验**上游半死（连上但不吐字、吐到一半断开）与 429 配额打满；
  后两者的判据分别属于 T4.6（停止/断流，见 frontend/probe/aichat.mjs）与 T4.1（预算熔断，见 90006）。
- 熔断是**进程内**状态：Redis 没跑（6379 无监听），跨实例的半开单探针语义至今只在单进程下验过。
- 离线话术的内容质量没做机器判据（只钉了「不是同一条复读」），那是论文侧的主观评价，不属于 Gate4。
